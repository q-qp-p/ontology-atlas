## 2026-10-15 — Group the MCP server modules by responsibility

**Why**: `mcp/src/` held 140 files directly, so finding the owner of one tool meant scanning a flat list. 112 now sit in 16 folders by what they do; the entry point, schema, parser, query, validate and whole-server suites stay at the root (28 files). The gate fires only because the tool registry and tool definitions changed their import paths.
**Prior**: 2026-10-11 "Split the MCP tool schema fragments by subject" set the pattern followed here: move verbatim, no barrel, importers name the owning file. 2026-08-30 "The CLI executes the MCP modules instead of copying them" stands: the CLI's loader now names `group/file.mjs`. No tool name, argument, schema, description or response changes.
**Decision**: Modules moved verbatim and every consumer follows the new path: the package `files` list, the CLI loader names, the app's re-export bridges, the `.mcpb` bundle's stripped typed module, check routing and vault citations. The MCP integration suite (159), CLI integration (319), MCP unit tests (1,344) and the contract suite (3,261) pass, and the compact brief keeps its four qualifier units on the known task.
**Dissent**: A flat folder keeps one `ls` for every module; answered by `server/registry.mjs` and the tool definitions, which name every tool and its owning module in one place, not by a re-export barrel.
**Falsifier**: A tool's `tools/list` entry or response differs from the previous layout, a packed install or the `.mcpb` bundle fails to load a module, or a test that ran before no longer runs.
**Owner**: Project owner; asked on 2026-10-14 to split every folder that needs it and to group what can be grouped.
